# Structured SQL Mastery Notes

## SELECT basics
The SELECT statement forms the foundational cornerstone of all Structured Query Language data retrieval operations. Its primary objective is projectively selecting attributes and computing expressions from one or more target relations designated in the mandatory FROM clause. In relational algebra, projection extracts vertical slices of tuples matching desired column specifications. Developers specify either explicit column names or an asterisk symbol to retrieve all attributes belonging to the table schema, though explicit enumeration is universally encouraged for schema stability, performance optimization, and memory efficiency. Beyond simple attribute retrieval, the SELECT clause supports computed arithmetic expressions, string manipulation functions, constant literal expressions, and type transformations. To present clear and human-readable result sets, column alias designations using the optional AS keyword rename output headers seamlessly. Furthermore, because relational databases store multiset collections allowing duplicate row values, SQL provides the DISTINCT keyword directly preceding column definitions to enforce duplicate tuple elimination from the final projected output set, filtering identical value vectors across specified fields.

Consider a practical worked example querying an enterprise employee repository table named staff containing employee_id, first_name, last_name, salary, and department_id:
SELECT DISTINCT department_id, first_name || ' ' || last_name AS full_name, salary * 1.10 AS adjusted_salary FROM staff;
In this query, explicit column projection avoids scanning unneeded metadata. The string concatenation operator joins names under the alias full_name, arithmetic scales salaries by ten percent, and DISTINCT guarantees unique rows in the projected output stream. When executing this projection, the database processes table metadata, calculates computed columns row-by-row, and filters redundant tuple vectors before streaming records to the client application. Failing to explicitly project required fields can lead to costly full-table serialization and network bandwidth bottlenecks.

Best practices dictate avoiding SELECT * in production application services. When underlying relational table definitions evolve through added or reordered attributes, wildcard queries can unexpectedly break client deserialization models, bloat buffer pools with unwanted binary objects, and prevent the relational optimizer from leveraging index-only covering scans.

## WHERE
The WHERE clause provides horizontal row-level filtering within relational queries, operating directly upon tuples produced by the FROM clause prior to any aggregation or grouping logic. It evaluates a boolean search predicate for each individual candidate record; only tuples evaluating strictly to TRUE are retained in the execution pipeline, while FALSE or UNKNOWN rows are excluded. SQL employs three-valued logic (3VL) because NULL represents missing or indeterminate information. Consequently, direct comparisons with NULL using standard equality operators return UNKNOWN rather than TRUE, requiring the explicit predicates IS NULL and IS NOT NULL for accurate absence validation. The WHERE predicate supports standard relational comparison operators including equality, inequality, and numeric comparisons, alongside composite logical conjunctions using AND, OR, and NOT. Range evaluation is succinctly handled via the BETWEEN operator, whereas set membership qualification is specified through the IN operator. String pattern matching is accomplished using the LIKE operator, leveraging percent symbols as multi-character wildcards and underscores as single-character position placeholders.

Review this worked example demonstrating multi-conditional filtering on an orders table with columns order_id, customer_id, order_status, total_amount, and shipped_date:
SELECT order_id, customer_id, total_amount FROM orders WHERE order_status IN ('COMPLETED', 'SHIPPED') AND total_amount BETWEEN 100.00 AND 500.00 AND shipped_date IS NOT NULL;
In this scenario, candidate rows are evaluated prior to any downstream operations. The IN predicate checks set membership across permitted status strings, BETWEEN confirms numeric boundaries inclusively, and IS NOT NULL prevents missing shipment dates from evaluating to UNKNOWN. If a predicate tests equality against NULL (such as shipped_date = NULL), SQL three-valued logic produces UNKNOWN, causing silent row omission. Applying indexed columns in WHERE predicates significantly reduces disk page reads and accelerates index scans.

A critical design consideration in relational query construction is predicate sargability (Search Argument Able). Wrapping filtered columns inside deterministic scalar functions, such as WHERE UPPER(last_name) = 'SMITH', prevents relational query optimizers from utilizing standard b-tree index lookups, forcing expensive full-table scans unless functional indexes have been explicitly materialized.

## ORDER BY
The ORDER BY clause establishes deterministic physical sequencing of the result set tuples returned to the client application. By fundamental relational database theory, tables and intermediate relational operations represent unordered multisets; therefore, predictable sorting is never guaranteed unless an explicit ORDER BY clause is appended to the query. Sort ordering is commanded via the ASC keyword for ascending direction (the default) or DESC for descending direction. Sorting criteria can encompass multiple distinct attributes, evaluated left-to-right in hierarchical precedence order: secondary columns resolve identical attribute ties present in primary ordering specifications. Relational systems also provide explicit NULL ordering control via NULLS FIRST or NULLS LAST directives to resolve indeterminate placement across ascending or descending sorting modes. While column positions or SELECT list aliases can be referenced within ORDER BY, referencing standard qualified column identifiers preserves query maintainability and protects against unintended positional shifts during subsequent schema modifications.

Examine this worked example demonstrating multi-column hierarchical sorting on an inventory table with columns warehouse_id, product_category, unit_price, and stock_quantity:
SELECT warehouse_id, product_category, unit_price, stock_quantity FROM inventory ORDER BY product_category ASC, unit_price DESC NULLS LAST, stock_quantity ASC;
Here, result rows are initially grouped sequentially by product_category in ascending alphabetical sequence. For products sharing an identical category, the secondary sorting directive physicalizes ordering by unit_price in descending magnitude, placing expensive items first while pushing any unpriced items to the end using NULLS LAST. Any remaining ties are deterministically resolved by stock_quantity. Because sorting is computationally intensive, backing high-frequency ORDER BY columns with composite b-tree indexes eliminates explicit sorting operations in the query execution plan.

Deterministic pagination relies entirely upon robust ORDER BY criteria. When combining sorting with row limiting clauses, failing to include a unique tie-breaking key attribute causes pagination drift, resulting in duplicate records or skipped rows across consecutive analytical batch requests.

## Aggregate functions
Aggregate functions perform mathematical reductions and statistical summarization across sets of relational tuples, condensing multiple input values into a single comprehensive scalar result. Core ANSI-standard aggregate functions include COUNT, SUM, AVG, MIN, and MAX. An indispensable semantic distinction exists between COUNT(*) and COUNT(column_name): COUNT(*) tallies all qualifying rows regardless of contents, whereas column-targeted aggregations systematically ignore and bypass NULL values before computing totals or arithmetic averages. If an aggregate function like SUM or AVG processes an empty set or a column containing exclusively NULL values, it evaluates to NULL, whereas COUNT reliably yields zero. Aggregations can integrate the DISTINCT modifier internally, as exemplified by COUNT(DISTINCT department_id), to restrict computations solely to unique non-null values. Aggregate functions operate across the entire qualifying relation unless partitioned into discrete subgroups through the companion GROUP BY clause, and they cannot appear directly inside a WHERE clause due to query lifecycle execution ordering.

Consider this worked example analyzing payroll metrics across an enterprise salary relation named compensation:
SELECT COUNT(*) AS total_staff_count, COUNT(bonus) AS bonus_recipients_count, AVG(base_salary) AS average_salary, MAX(base_salary) AS maximum_salary, SUM(COALESCE(bonus, 0)) AS total_bonus_disbursed FROM compensation;
Notice how COUNT(*) reflects the complete headcount of records, whereas COUNT(bonus) reflects only rows where bonus is not null. Similarly, AVG computes the mean solely across populated salaries. By wrapping bonus with COALESCE inside the SUM function, missing bonuses are safely evaluated as zero rather than propagating null anomalies. Aggregation occurs across the entire active tuple multiset, transforming thousands of raw records into a concise statistical summary vector.

Furthermore, aggregate functions execute in the query processing lifecycle after the FROM and WHERE stages. Attempting to evaluate expressions like WHERE salary > AVG(salary) generates an immediate syntax error. To accomplish comparative filtering against summary metrics, developers must employ auxiliary subqueries or post-aggregation filters.

## GROUP BY
The GROUP BY clause partitions an input relational row set into discrete summary buckets based on shared equivalences across one or more grouping attributes. Once grouped, aggregate functions evaluate independently within each separate partition rather than collapsing the entire table into a single global scalar. A paramount structural constraint governing grouped queries is the Single-Value Rule: every column referenced in the SELECT clause, ORDER BY clause, or HAVING clause must either appear explicitly among the GROUP BY attributes or be wrapped securely inside an aggregate function. Attempting to project an unaggregated, ungrouped column produces an unambiguous relational syntax violation because such an attribute could possess multiple conflicting values per group bucket. In query processing sequence, WHERE clause filters discard non-qualifying tuples before grouping occurs, ensuring only relevant candidate rows are categorized. Multi-column grouping forms compound hierarchical partitions representing every distinct cartesian combination of values existing across the grouped dimensions.

Study this worked example calculating regional sales performance on a transactions table containing region_name, payment_method, transaction_amount, and transaction_status:
SELECT region_name, payment_method, COUNT(*) AS transaction_volume, SUM(transaction_amount) AS regional_gross_revenue FROM transactions WHERE transaction_status = 'APPROVED' GROUP BY region_name, payment_method ORDER BY region_name ASC, regional_gross_revenue DESC;
In this execution, the WHERE clause first discards unapproved records. Next, GROUP BY partitions the approved transactions into composite buckets matching each distinct combination of region_name and payment_method. The aggregate expressions evaluate independently inside each partition bucket. Attempting to include an unaggregated attribute such as customer_email in the SELECT list violates the Single-Value Rule and triggers an immediate database exception.

Relational storage engines evaluate GROUP BY either through in-memory sorting or hash aggregation algorithms. Creating matching composite indexes on the exact grouping columns allows the query engine to scan records in pre-sorted key order, bypassing costly intermediate disk spill operations.

## HAVING
The HAVING clause establishes conditional filtering criteria applied directly to grouped row buckets and aggregate calculation results, serving as the post-aggregation counterpart to the row-level WHERE filter. Because relational engines process clauses in a strictly disciplined logical order—FROM, then WHERE, followed by GROUP BY, and subsequently HAVING—the WHERE clause cannot reference aggregate function results or group properties since aggregation has not yet occurred at that phase of query execution. The HAVING clause resolves this limitation by evaluating boolean predicates against aggregate calculations, such as filtering for groups where COUNT(*) exceeds a specified threshold or AVG(salary) surpasses a budgetary limit. While HAVING can technically evaluate conditions on raw grouping columns, relational performance best practices dictate filtering non-aggregated row criteria in the earlier WHERE clause to minimize intermediate data volume prior to costly hashing, sorting, and grouping operations.

Examine this worked example identifying high-volume production departments from an operational tasks table containing department_id, task_priority, duration_hours, and task_status:
SELECT department_id, COUNT(*) AS total_tasks, AVG(duration_hours) AS avg_duration FROM tasks WHERE task_status = 'COMPLETED' GROUP BY department_id HAVING COUNT(*) >= 50 AND AVG(duration_hours) > 4.5 ORDER BY total_tasks DESC;
Here, initial row filtering in the WHERE clause excludes incomplete tasks. Surviving tasks are bucketed by department_id. Subsequently, the HAVING clause evaluates the aggregate predicates, discarding any department with fewer than fifty completed tasks or an average duration below four and a half hours. This illustrates the fundamental division of responsibility: WHERE discards raw tuples before grouping, whereas HAVING eliminates entire aggregate buckets based on summarized characteristics.

Confusing WHERE and HAVING remains one of the most common relational query design mistakes. Placing static column conditions into HAVING forces the database engine to group unneeded rows into memory before filtering, degrading performance by orders of magnitude compared to pruning those rows early in WHERE.

## JOINs
The JOIN operator reconstructs relational associations across distinct tables by correlating foreign key references with primary key identifiers or evaluating general boolean join predicates. INNER JOIN retains only tuples that satisfy the join condition across both participating tables, discarding any non-matching rows. OUTER JOIN variants preserve unmatched rows from one or both sides: LEFT OUTER JOIN retains every record from the left-hand relation and populates right-hand attributes with NULL when no matching counterpart exists; RIGHT OUTER JOIN mirrors this behavior for the right relation; and FULL OUTER JOIN retains all records from both relations, supplying NULLs for missing values on either side. CROSS JOIN computes the unconstrained cartesian product of two relations, pairing every row from the first with every row from the second. The ON clause specifies the logical criteria binding relational entities together, distinguishing relationship linkage mechanics from post-join row filtering traditionally designated in the WHERE clause.

Analyze this worked example combining customer profiles with order histories using both INNER and LEFT joins across customers, orders, and order_items:
SELECT c.customer_id, c.customer_name, o.order_id, COALESCE(o.order_status, 'NO_ORDERS') AS status, COALESCE(SUM(i.item_price * i.quantity), 0.00) AS total_spent FROM customers c LEFT OUTER JOIN orders o ON c.customer_id = o.customer_id LEFT OUTER JOIN order_items i ON o.order_id = i.order_id GROUP BY c.customer_id, c.customer_name, o.order_id, o.order_status;
By employing LEFT OUTER JOIN, prospective customers who have never placed an order are preserved in the result set rather than dropped. The ON condition dictates the relational stitch point between primary keys and foreign keys. Aggregate functions compute total spending per order, substituting zero for non-existent line items using COALESCE.

Join performance depends on join algorithms selected by the query optimizer: nested loop joins for small indexed relations, hash joins for large unindexed sets, and merge joins for pre-sorted inputs. Ensuring foreign key columns are indexed eliminates costly full-table scans during relational joins.

## Subqueries
A subquery represents an auxiliary nested SELECT query enclosed within parentheses embedded inside a larger parent SQL statement. Subqueries are categorized structurally by dimensionality: scalar subqueries return exactly one row and one column, column subqueries yield a single column across multiple rows, and table subqueries produce two-dimensional relations often referenced as derived tables within the FROM clause. Functionally, subqueries are classified as either non-correlated or correlated. Non-correlated subqueries execute independently of outer queries, producing static values or sets consumable by outer operators such as IN, ANY, and ALL. Conversely, correlated subqueries reference one or more columns from the enclosing outer query, necessitating conceptual re-evaluation for each candidate outer row processed. Relational predicate operators like EXISTS and NOT EXISTS efficiently test for the existence of matching tuples within correlated subqueries, terminating evaluation immediately upon locating the first qualifying match.

Examine this worked example demonstrating both a correlated subquery with EXISTS and an uncorrelated scalar subquery on an accounts and ledger table:
SELECT a.account_id, a.account_holder, a.balance FROM accounts a WHERE a.balance > (SELECT AVG(balance) FROM accounts) AND EXISTS (SELECT 1 FROM ledger l WHERE l.account_id = a.account_id AND l.transaction_date >= CURRENT DATE - 30 DAYS);
The first subquery is scalar and non-correlated: it executes once globally to establish the overall average account balance. The second subquery is correlated: it references the candidate outer row's a.account_id to inspect whether ledger entries exist within the past month. The EXISTS predicate evaluates efficiently by performing an early-exit check as soon as one matching transaction is located.

Modern relational optimizers frequently rewrite uncorrelated and correlated subqueries into equivalent semi-joins or hash joins during cost-based optimization. However, understanding subquery scope rules and null-sensitivity in NOT IN predicates is essential to avoid unexpected empty result sets.

## Window functions
Window functions compute analytical calculations, cumulative statistics, moving averages, and rankings across a designated partition of table rows related to the current evaluation row, without collapsing the individual rows into a single summary output tuple. Unlike GROUP BY, which reduces row cardinality, window functions preserve the original row identity while projecting computed metrics alongside base attributes. A window function is distinguished syntactically by the mandatory OVER clause, which establishes the window boundary. Within the OVER specification, the PARTITION BY sub-clause divides rows into analytical subsets, the ORDER BY sub-clause defines the deterministic sequence of evaluation within each subset, and the framing sub-clause (such as ROWS BETWEEN) designates the precise sliding window boundaries. Key window functions include ranking functions like ROW_NUMBER, RANK, and DENSE_RANK, as well as positional value access functions such as LAG and LEAD.

Study this worked example computing financial rankings and running balance totals across departmental transactions:
SELECT transaction_id, department_id, employee_id, amount, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY amount DESC) AS dept_rank, SUM(amount) OVER (PARTITION BY department_id ORDER BY transaction_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumulative_dept_spending, LAG(amount, 1) OVER (PARTITION BY department_id ORDER BY transaction_date) AS prior_transaction_amount FROM department_expenses;
In this query, each individual transaction retains its unique row position. The ROW_NUMBER function assigns ordinal ranks per department based on transaction magnitude. Concurrently, the SUM window function computes a cumulative moving total bounded from the start of the partition up to the current row, and LAG retrieves the previous transaction's expenditure without requiring a costly self-join.

Window functions execute very late in the query lifecycle, immediately following HAVING and preceding final ORDER BY. Consequently, window function outputs cannot be referenced directly within WHERE or HAVING clauses; filtering over windowed values requires enclosing the query in a common table expression (CTE) or derived table.
